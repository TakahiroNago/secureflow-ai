## 1. 対象範囲

MVP（Phase 1〜3）：React SPA、Laravel API、Queue Worker、PostgreSQL、Redis、OpenAI API 連携（Phase 2〜）、ローカル Docker 環境。外部サービスへの実操作（Phase 4）、AWS（Phase 5）は対象外だが、拡張時に本モデルを更新する。

## 2. 保護資産

| ID | 資産 | 重要度 |
|---|---|---|
| A1 | ユーザーが入力する業務内容（個人情報・機密情報を含みうる） | 高 |
| A2 | 認証情報（パスワードハッシュ、セッション） | 高 |
| A3 | OpenAI APIキー | 高 |
| A4 | 承認の完全性（承認内容と実行内容の一致） | 高 |
| A5 | 監査ログの完全性 | 高 |
| A6 | 組織間・ユーザー間のデータ分離 | 高 |
| A7 | AI利用予算 | 中 |
| A8 | システムプロンプト（秘密は含めないが、攻撃の足掛かりになりうる） | 低 |

## 3. 脅威主体

| ID | 主体 | 想定 |
|---|---|---|
| U1 | 未認証の外部攻撃者 | ローカル環境でも将来の公開を想定 |
| U2 | 悪意ある、または不注意な member | 自分の権限内で攻撃入力・他人データの参照を試みる |
| U3 | 悪意ある admin | 自己承認、監査ログ改ざんを試みる |
| U4 | 間接的攻撃者 | ユーザーが貼り付けた外部文書（メール・Web）に指示を埋め込む |
| U5 | AIプロバイダ側の異常 | 不正形式・悪意あるように見える出力、障害 |
| U6 | サプライチェーン | 依存パッケージ・コンテナイメージの脆弱性 |

## 4. データフローと信頼境界

```
[U1/U2/U3 Browser] ─TB1─▶ [nginx] ─▶ [Laravel API] ─TB5─▶ [PostgreSQL]
                                         │    └──────────▶ [Redis]
       [U4 外部文書] ─(貼付)─▶ TB1        │
                                         ▼
                                     [Worker] ─TB2─▶ [OpenAI API] ─TB3─▶ [Worker]
                                         │
[Browser] ◀─TB4─ [Laravel API] ◀─────────┘
```

## 7. 残存リスク

公開環境へ移行する前に満たす条件は [security-design.md §22](security-design.md) に集約した。本表の「公開環境の前提」はそれを指す。MVP の完成の判定（[mvp-completion.md](mvp-completion.md)）に残存リスクは含めず、受容した理由は本表のとおりである。

| ID | 残存リスク | 受容理由・今後の対応 |
|---|---|---|
| R-01 | 未知・高度なプロンプトインジェクションは検出できない | 検出は補助層。AIに実行権限がなく、人間の承認が必須のため影響は「不適切な提案」に限定される |
| R-02 | 氏名・住所等の個人情報はマスキングされずAIプロバイダへ送信されうる | 画面・ドキュメントで明示。将来、固有表現抽出等を検討。プロバイダのデータ保持条件をPhase 2前に確認 |
| R-03 | DB所有者・スーパーユーザーは監査ログトリガーを無効化し、チェーン全体を再計算でき、末尾の行の削除とヘッドの巻き戻しもできる。**DB の中の情報だけでは検出できない** | MVPでは `audit:head` の出力の手動保管によって、保管時点までの範囲のみ検出できる（保管していなければ検出できない）。将来、外部ストレージへの自動退避 |
| R-04 | 悪意ある admin 2名の共謀による承認 | 職務分掌の限界。監査ログで事後追跡 |
| R-05 | AIの誤った提案を承認者が見落とす | MVPは模擬実行のみで実害なし。Phase 4 では操作ごとの影響表示を強化 |
| R-06 | ローカル開発環境の HTTP 運用（Secure Cookie 不可） | ローカル限定・127.0.0.1バインド。公開環境では HTTPS 必須 **工程5-1：** 公開環境は ALB で TLS を終端し、`APP_URL` が https のため Secure Cookie と https の URL 生成が有効になり、本番の web イメージが HSTS を付ける（[security-design.md §22 A-1](security-design.md)）。ALB と nginx の間は VPC 内の HTTP である |
| R-07 | 検出できない形式の認証・秘密情報（独自形式のキー、分割された値等）はマスキング・停止されずに送信されうる | 検出漏れがないことは保証しない。画面・APIで明示。ルールを継続的に追加 |
| R-08 | 組織に admin が1名しかいない場合、その admin が作成したワークフローは実行できない | 職務分掌を優先した仕様として受容（D13）。運用上は admin を2名以上置く |
| R-09 | メールアドレスを知る第三者は、対象者の新規ログインを15分間止め、繰り返すことができる（T-33） | 総当たり対策とのトレードオフとして受容。影響は新規ログインに限定され、既存セッションと承認・実行は維持される。監査ログの `auth.locked`・`auth.login_failed`（工程1-3）で検知する |
| R-10 | ロック中でも、既に侵害された既存セッションは失効しない（ロックは侵害対応の手段ではないため） | `is_active = false` とパスワード変更で失効できる。侵害の兆候に応じた失効の仕組みは将来追加できるようにする（[security-design.md §12](security-design.md)） |
| R-11 | `audit_append()` は actor が同じ組織に属することしか確認できない。app ロールを奪取した攻撃者は、同じ組織の別のユーザーを actor として記録でき、事実と異なるイベントも追記できる | DB は実際のログイン本人を独立に証明できない。アプリでは actor を認証済みのサーバー側コンテキストから決定し、任意の actor を指定できる API を設けない。app ロールの奪取は T-29 の対策で抑止する。追記されたイベントはチェーンから削除できないため、事後の調査の材料は残る |
