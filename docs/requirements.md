## 1. プロジェクト概要

### 1.1 目的

AIを活用して業務を効率化すると同時に、AI利用に伴うセキュリティリスクを管理・軽減するWebアプリケーションを開発する。

AIによる業務処理、実行権限の制御、人間による承認、セキュリティ検査、監査ログを統合する。

単なるAIチャットアプリではなく、企業でのAI業務利用を想定した、安全なAIワークフロー管理システムを目指す。

### 1.2 解決する課題

- AIを使った業務自動化の仕組みが不足している。
- AIに過剰な権限を与えることによるリスクがある。
- プロンプトインジェクションによる不正な指示変更を防ぎたい。
- 個人情報や機密情報のAIへの送信を制御したい。
- AIが実行した操作を追跡・監査したい。
- AIの利用状況やAPIコストを把握したい。
- AIアプリケーションのセキュリティを継続的に検証したい。

### 1.3 想定ユーザー

- AIを業務に導入する企業の管理者
- 業務効率化を担当するエンジニア
- AIアプリケーション開発者
- セキュリティ担当者
- 小規模チームの管理者

### 1.4 基本コンセプト

「AIに仕事を任せる。しかし、AIに無制限の権限は与えない。」

AIが業務内容を分析・提案し、セキュリティレイヤーが処理内容と権限を検証する。

重要な操作は人間の承認を経て実行する。

## 2. 開発方針

### 2.1 MVPの開発範囲

最初のバージョンでは、以下の機能を実装する。

1. ユーザー認証
2. ダッシュボード
3. AIによる文章分析・タスク生成
4. AIワークフロー管理
5. 実行前のセキュリティ検査
6. 人間による実行承認
7. 個人情報・機密情報の検出とマスキング
8. プロンプトインジェクション検査
9. 操作履歴・監査ログ
10. セキュリティテスト結果の表示

### 2.2 開発段階

- Phase 1：基本アプリケーションとAIワークフロー
- Phase 2：セキュリティ制御と監査ログ
- Phase 3：自動セキュリティテスト
- Phase 4：外部サービス連携
- Phase 5：AWSデプロイと監視

MVPではPhase 1〜3を中心に実装する。

Phase 4〜5は拡張可能な設計にしておくが、初期実装には含めない。

【v1.1】

- Phase 1ではモックAIプロバイダーのみを使用する。実際のAI API（OpenAI）への接続は、Phase 2でマスキング・出力検証が完成し、必要なセキュリティテストを通過するまで有効化しない。
- 監査ログの基盤（追記専用テーブルと記録サービス）はPhase 1で実装する。
- 開発はWSL2のLinuxファイルシステム内で行い、PHP・ComposerはDockerコンテナ内で実行する。

## 4. 機能要件

### 4.1 ユーザー認証

以下を実装する。

- ログイン
- ログアウト
- パスワードの安全な保存
- 認証が必要なAPIの保護
- 認証されていないユーザーのアクセス制限
- セッション管理

将来的な複数ユーザー・組織管理を想定し、ユーザーと業務データの関連付けを適切に設計する。

【v1.1】

- ロールは admin / member / auditor の3種類とする。
- ユーザーは管理用コマンドで作成する。初期データ投入ではログイン可能な固定ユーザーを作成しない。公開サインアップは実装しない。
- 連続したログイン失敗でアカウントを一時ロックする。
- セッションは無操作30分・絶対12時間で失効する。
- organizations テーブルを最初から作成し、全業務データを組織に関連付ける。

### 4.2 ダッシュボード

ログイン後に表示する管理画面。

表示項目：

- 登録ワークフロー数
- 実行済みタスク数
- 承認待ちタスク数
- セキュリティ警告数
- 検出されたリスク数
- AI API利用状況
- 最近の操作履歴

グラフやカードを利用して、システムの状態を把握できるようにする。

### 4.3 AI業務自動化

ユーザーが文章を入力すると、AIが内容を分析してタスクを生成する。

例：

入力：
「毎週の売上報告を作成して、重要な変化をまとめてください。」

AIの出力：

- タスク名
- タスクの説明
- 必要な処理
- 優先度
- 実行に必要な権限
- 実行内容の概要

MVPでは、AIによる文章分析とタスク生成までを実装する。

生成したタスクはデータベースに保存する。

AIの出力は常に未信頼データとして扱い、スキーマ検証を実施する。

AIの回答を直接コードやシェルコマンドとして実行してはならない。

【v1.1】

- AIには実行権限・ツール呼び出し能力を与えず、AIは提案（JSON）を返すのみとする。
- 「実行に必要な権限」はサーバーが操作種別から導出する。AIが申告した権限は照合にのみ使い、認可には使わない。
- AI分析は非同期処理（キュー＋状態確認）とする。
- 保存するのはマスキング後の文章のみとし、入力原文は保存しない。

### 4.4 ワークフロー管理

ワークフローの状態を管理する。

状態：

- Draft：下書き
- Pending：承認待ち
- Approved：承認済み
- Running：実行中
- Completed：完了
- Rejected：却下
- Failed：失敗

ユーザーはワークフローの内容を確認できる。

実行内容を変更した場合は、以前の承認を無効にする。

【v1.1】

- 実行内容の変更（タスクの編集・追加・削除）のたびに新しいリビジョンを作成する。
- Pending / Approved 状態で編集された場合は Draft に戻し、再提出・再承認を必須とする。
- Running / Completed 状態のワークフローは編集できない。
- Rejected / Failed 状態からは、新しいリビジョンとして Draft に戻して修正できる（reopen）。

### 4.5 承認フロー

AIが生成したタスクを実行する前に、ユーザーが確認・承認する。

表示内容：

- 実行する処理
- 使用するAI機能
- 対象データ
- 必要な権限
- セキュリティ検査結果
- 実行による影響

ユーザーが承認するまでは外部への操作を行わない。

承認後も、実行直前に権限とセキュリティ状態を再検証する。

承認は対象となる処理内容に紐付ける。承認後に処理内容が変更された場合は再承認を要求する。

MVPでは、外部サービスへの実操作は行わず、承認された処理を模擬実行する。

【v1.1】承認権限

- 承認・却下できるのは admin のみとする。
- admin は他のユーザーが作成したワークフローのみ承認できる。自分が作成したワークフローは、admin であっても承認できない。
- auditor には承認権限を与えない。member にも承認権限はない。
- 申請者と承認者は必ず別ユーザーとする。
- 承認可能な admin がいない場合、そのワークフローは承認されず、実行できない。

【v1.1】承認の紐付け

- 承認は、ワークフローID・リビジョン・全タスク・操作種別・権限・適用ポリシーのバージョンを含む正規化データから計算したSHA-256ハッシュ（承認ハッシュ）に紐付ける。
- 1リビジョンにつき承認・却下の決定は1回のみとする。
- 中リスク（Medium）以上の検出結果を含む場合、承認時にリスク確認を必須とする。

### 4.6 セキュリティ検査

AIに処理を依頼する前に、入力内容を検査する。

#### A. プロンプトインジェクション対策

以下を検出対象とする。

- システムプロンプトの無効化を要求する指示
- 内部指示や秘密情報の開示要求
- 開発者権限へのなりすまし
- 外部コンテンツからの不正な指示
- AIの制限を回避しようとする入力

検出結果：

- Low
- Medium
- High
- Critical

注意事項：

単純なキーワード検出だけで安全性を保証しないこと。

ルールベースの検査を基本とし、必要に応じて追加のAI判定を行う。

検出に失敗する可能性があることを前提に、権限の制限や承認フローを独立した防御層として実装する。

【v1.1】

- 検出ルールは完全な防御手段ではない。最終防御層は「AIに実行権限を与えないこと」とする。
- 検出結果の重大度（severity：Low / Medium / High / Critical）と処理動作（action）を分離して定義する。
- プロンプトインジェクションの処理動作：High / Critical は処理停止（AIを呼び出さない）、Medium は警告付きで続行、Low は記録のみ。
- AIによる追加判定を行う場合、その結果はリスクを引き上げる方向にのみ反映する。

#### B. 個人情報・機密情報の検出

以下を検出対象とする。

- メールアドレス
- 電話番号
- APIキー
- アクセストークン
- パスワード
- 秘密鍵
- クレジットカード番号形式の文字列

検出した情報はマスキングする。

例：

`test@example.com`

↓

`[EMAIL_REDACTED]`

マスキング後のデータをAIに送信する。

原文を不必要にログへ保存しない。

誤検知・検出漏れがあることを考慮し、セキュリティ検査の結果をユーザーに表示する。

【v1.1】

- 検出対象にマイナンバー形式を追加する。
- 個人情報と認証・秘密情報で処理動作を分ける。
  - メールアドレス、電話番号、カード番号、マイナンバー等の個人情報は、検出・マスキング後に処理を続けられる。
  - APIキー、アクセストークン、パスワード、秘密鍵（PEM等）の認証・秘密情報は、原則として処理を停止する。
- 重大度（severity）と処理動作（action）は別々に定義する。
- マスキングできなかった場合（処理エラー、マスキング後の再検査で検出が残る等）は fail closed とし、処理を停止する。
- 検出器は完全ではない。氏名・住所など、MVPで十分に検出できない情報があることを画面・APIレスポンス・ドキュメントで明示し、検出されなかった情報が存在しないとは保証しない。

#### C. AI出力の検査

AIから返された文章を検証する。

- 期待するJSONスキーマとの一致
- 不正な形式の検出
- HTMLやスクリプトの無害化
- 不許可の操作内容の検出
- 機密情報の出力検査

AI出力をそのままHTMLとしてレンダリングしない。

【v1.1】

- システムプロンプトにカナリア文字列を埋め込み、出力への出現でシステムプロンプト漏洩を検知する。
- AI出力はReactのテキスト描画を基本とする。HTML除去だけに依存せず、HTMLとして描画する機能は原則禁止する。

### 4.7 権限管理

AIに許可する操作を明確に定義する。

例：

| 操作 | MVPでの扱い |
|---|---|
| 文章の分析 | 許可 |
| タスクの生成 | 許可 |
| タスクの保存 | サーバー側で制御 |
| 外部メール送信 | 禁止 |
| ファイル削除 | 禁止 |
| シェルコマンド実行 | 禁止 |
| データベース直接操作 | 禁止 |
| 外部APIの自由な呼び出し | 禁止 |

AIが任意のツールを呼び出せる設計にしない。

ツール実行機能を追加する場合は、サーバー側で定義した許可リストを利用する。

### 4.8 監査ログ

以下のイベントを記録する。

- ログイン
- ログアウト
- タスク作成
- タスク更新
- AI API呼び出し
- セキュリティ検査
- 承認
- 却下
- 実行
- 実行失敗

ログには以下を含める。

- イベントID
- ユーザーID
- イベント種別
- 発生日時
- 対象リソース
- 実行結果
- 必要に応じてリスクレベル

パスワード、APIキー、アクセストークン、未加工の個人情報、不要な相談内容などをログに記録しない。

一般ユーザーが監査ログを改ざんできない設計にする。

【v1.1】

- MVPでは、追記専用のDB権限、UPDATE / DELETE / TRUNCATE を拒否するトリガー、ハッシュチェーンを実装する。
- ハッシュの外部ストレージへの退避は将来の拡張候補とする。

### 4.9 セキュリティテスト

以下のテストケースを用意する。

| テスト | 期待結果 |
|---|---|
| 通常の業務依頼 | 正常にタスク生成 |
| プロンプトインジェクション | 検知・警告 |
| APIキー形式の文字列 | 検出・マスキング |
| メールアドレス | 検出・マスキング |
| 未認証APIアクセス | 401 |
| 権限のない操作 | 403 |
| 不正なJSON | バリデーションエラー |
| 未承認タスクの実行 | 拒否 |
| 承認後の内容変更 | 再承認要求 |
| HTMLスクリプトの出力 | 無害化 |
| 大量リクエスト | レート制限 |
| 他ユーザーのデータ参照 | アクセス拒否 |

テスト結果をダッシュボードに表示する。

セキュリティテストは通常のユニットテストと分離し、実際の攻撃シナリオを模した検証として管理する。

【v1.1】

- テスト結果の表示は、アプリ内のセキュリティ自己診断機能で行う。HTTPレベルのテスト（401、CSRF、レート制限等）はGitHub ActionsのCIで別途実行する。
- 別組織のデータにアクセスできないことをテストする。
- 自己承認ができないこと、および秘密情報を含む入力で処理が停止することをテストする。
- 上表の「APIキー形式の文字列」の期待結果は「検出・処理停止」とする（認証・秘密情報は原則停止のため）。メールアドレスは引き続き「検出・マスキング」（マスキング後に処理続行）とする。

## 5. 非機能要件

### 5.1 セキュリティ

OWASPの以下の資料を参考にする。

- OWASP Top 10
- OWASP Top 10 for LLM Applications
- OWASP ASVS

特に以下を重視する。

- 認証・認可
- SQLインジェクション対策
- XSS対策
- CSRF対策
- SSRF対策
- レート制限
- セッション保護
- 入力値検証
- APIキー管理
- 個人情報保護
- プロンプトインジェクション対策
- 過剰な権限付与の防止

AIセキュリティだけでなく、通常のWebアプリケーションとしてのセキュリティも確保する。

【v1.1】

- UUIDを認可の代わりにしない。すべてのAPIで組織・ユーザー・ロールの認可を実施する。
- 同時承認・承認後の編集・二重実行・実行中の障害を考慮し、DBトランザクション・行ロック・一意制約で制御する。
- PostgreSQLのロールはowner（マイグレーション専用）とapp（アプリ実行用）に分離する。
- DBとRedisのポートは原則ホストに公開しない。

### 5.2 可用性

- AI APIのタイムアウト設定
- APIエラー時の適切なエラーハンドリング
- 必要に応じたリトライ
- 二重実行防止
- 非同期処理への対応

### 5.3 保守性

- MVCを基本とする責務分離
- ビジネスロジックのサービス層への分離
- AIプロバイダーの抽象化
- セキュリティ検査の独立した実装
- テストコードの整備
- 環境変数による設定管理

### 5.4 コスト管理

- AI APIの利用回数を記録
- トークン使用量を記録
- API呼び出しの上限設定
- 開発用のモックAIプロバイダーを用意
- AI APIが利用できない場合でも基本機能のテストが可能な構成

【v1.1】

- 上限は、組織ごとの月間トークン数、ユーザーごとの1日のAI分析回数、最大入力長で設定する。
- 実際のOpenAI API接続の前に、モデル、API仕様、データ保持、学習利用、送信データ範囲、レート制限等を確認する。

## 7. UI・デザイン方針

企業向けのセキュリティ管理SaaSとして、信頼感と視認性を重視する。

デザインの方向性：

- モダンなSaaS管理画面
- 落ち着いたネイビー・グレーを基調とする
- 情報を整理したカード型レイアウト
- リスクレベルを色分け
- グラフを活用
- 適切な余白
- レスポンシブ対応
- PCでの操作性を優先

単に装飾的な画面にせず、業務上必要な情報を短時間で把握できるUIにする。

## 12. Claude Codeへの開発指示

あなたはシニアソフトウェアエンジニア兼セキュリティエンジニアとして、本プロジェクトの設計・実装を担当する。

以下の方針を厳守すること。

### 12.1 開発の進め方

最初からすべての機能を一括実装しない。

まず以下を行う。

1. 開発環境と既存ファイルを確認する。
2. 要件を分析する。
3. システムアーキテクチャを提案する。
4. データベース設計を提案する。
5. API設計を提案する。
6. セキュリティ設計を提案する。
7. Phaseごとの実装計画を作成する。
8. 必要な技術選定について理由を説明する。

この段階ではファイルを変更せず、設計レビュー用のレポートを提示する。

ユーザーの承認後、Phase単位で実装する。

各Phaseの完了時には以下を報告する。

- 実装した機能
- 変更したファイル
- 実施したテスト
- テスト結果
- セキュリティ上の確認事項
- 残っている課題
- 次のPhase

### 12.2 セキュリティ上の禁止事項

- APIキーや秘密情報をソースコードにハードコードしない。
- `.env`をGitにコミットしない。
- AIの出力を信頼して直接実行しない。
- AIに任意のシェル実行権限を与えない。
- AIにデータベースへの直接アクセスを許可しない。
- 承認前に外部操作を行わない。
- 個人情報を不必要にログへ保存しない。
- エラー画面に内部情報や秘密情報を表示しない。
- セキュリティ検査を単一のAI判定だけに依存させない。

### 12.3 コード品質

- 可読性と保守性を重視する。
- 過度な抽象化を避ける。
- 責務を適切に分離する。
- 型安全性を重視する。
- テストを実装と同時に作成する。
- エラー処理を適切に実装する。
- 不必要な依存ライブラリを追加しない。
- 変更範囲を最小限にする。

### 12.4 ドキュメント

以下を作成する。

- README.md
- docs/architecture.md
- docs/database-design.md
- docs/api-design.md
- docs/security-design.md
- docs/threat-model.md
- docs/test-strategy.md
- docs/development-roadmap.md

### 12.5 最初に行うこと

要件を読み込み、まず設計フェーズを開始すること。

不明点や技術的な矛盾がある場合は、勝手に決定せず、選択肢と推奨案を提示すること。

特に、AIへの入力・出力の信頼境界、権限管理、承認フロー、機密情報の取り扱いについては、実装前に具体的な設計を示すこと。

**最優先事項は、機能の多さではなく、安全性・実用性・保守性を兼ね備えたMVPを完成させることである。**
